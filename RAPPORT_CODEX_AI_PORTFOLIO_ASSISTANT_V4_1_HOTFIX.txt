===== RAPPORT CODEX — AI PORTFOLIO ASSISTANT V4.1 HOTFIX =====

1. BUG GREETINGS
- Cause exacte : identifyLocalIntent comparait la salutation à une expression régulière exacte après une normalisation générale qui ne réduisait pas les répétitions. « salam » correspondait, mais « salaaaaam », « bonjourrr » et les alias bjr/bjour/slt n'appartenaient pas à la liste et partaient vers Groq.
- Fichiers concernés : language.ts, intent-resolver.ts, local-responses.ts et route.ts.
- L'appel Groq inutile pouvait ensuite exposer les erreurs de quota, réseau ou timeout à une simple salutation.

2. NORMALISATION AJOUTÉE
- Nouveau module conversational-normalization.ts.
- Pour les messages courts de 40 caractères maximum seulement : NFKC, minuscules, ponctuation/espaces, réduction de 3 lettres latines identiques ou plus, puis alias sûrs.
- Alias FR : bonjour, bjr, bjour, salut, slt, bonsoir, bsr, coucou. EN : hi/hii, hello, hey, yo. Darija/Arabizi : salam/salaam, slm, salam alikoum/3likom, labas, kidayr/ki dayr. Arabe : سلام, السلام عليكم, مرحبا, أهلا.
- Les expressions sont ancrées sur le message entier : salaires, hello world project et hi-tech architecture ne sont pas des greetings.
- Le message original reste utilisé partout ailleurs, notamment pour les entités, technologies, URLs et Groq.

4. BUG LOADING 0 %
- Cause racine : useState(shouldSkipLoading) produisait un état initial dépendant de l'environnement. Le serveur retournait false faute de window, alors que l'hydratation client pouvait lire sessionStorage=true. Cette divergence serveur/client rendait le montage de l'overlay non déterministe. La lecture/écriture de sessionStorage n'était pas protégée ; une exception empêchait le flux. Enfin, le timer final de sortie n'était pas nettoyé et aucun failsafe ne garantissait le démontage.
- Scénario : intro déjà vue ou stockage dans un état particulier, reload, rendu serveur avec loader 0 %, hydratation avec une décision différente ou interrompue, effet de progression non garanti, overlay restant au-dessus du contenu.
- ChatWidget n'écrit aucune clé de loading et ne partage aucun état avec Home ; il augmentait seulement la probabilité d'observer le reload problématique, sans en être la cause directe.

5. CORRECTION LOADING
- État initial déterministe commun serveur/client : checking.
- Après hydratation seulement, un useEffect lit sessionStorage dans try/catch et choisit loading ou complete.
- introSeen=true ou hash : portfolio direct. Valeur absente : animation normale. Stockage indisponible/invalide : fail-open vers le portfolio.
- handleLoadingComplete est stabilisé avec useCallback et protège l'écriture sessionStorage.
- Les timers sont nettoyés, y compris le timer de sortie.
- Failsafe parent de 5 secondes : le contenu reste toujours accessible même si l'animation échoue.
- data-testid a été ajouté sans changement visuel afin de vérifier le runtime.
